Class KcdLayers

Layer (storey/tier) assignment for components added to a design file (ADR §4.4c). The file's <Layer> integer is the legacy designer's hand-typed storey index — it filters the build in the Layer Manager and splits the texted top-view PDF into one page per tier. The legacy app cannot compute it (a 2D canvas has no answer to "what stands on what"), so designers maintain it by hand; the suite can, so additions derive their tier and an existing component's Layer is treated as designer evidence that is never rewritten and never "corrected".

Corpus-measured before writing (reference kcds, 9 multi-layer tabs, 128 deck placements): designer layers are clean non-interleaving height bands 9/9; the traversal tier below reproduces 102/128 hand assignments, and the misses are one file with privately inverted numbering (adoption keeps it) and tiers reached only by climbing links (adoption inherits them from the file's own bands). Height ALONE cannot draw the band line — the corpus holds a between-band gap equal to the largest within-band step (both 24") — which is why adjacency and footprint coincidence participate.

Assign(IEnumerable<KcdComponent>, IReadOnlyList<KcdComponentAddition>, IReadOnlyList<KcdLink>?)

Fills each addition's Layer from the tab's existing components and the other additions, in precedence order: an attachment takes its owner's layer; a part standing on a lower donor's footprint (within PdTolerance, more than SameLevelTolerance above) takes that donor's layer plus one — the storey relation; a part within a walkable step of a plan-adjacent donor joins that donor's layer; otherwise the nearest existing band by height; and with no donors at all, ground — layer 0. Additions are processed lowest first (attachments after their potential owners) and join the donor pool as they are assigned, so a tower born into an empty file still numbers its storeys 0/1/2 bottom-up.
