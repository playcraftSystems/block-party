Namespace Playcraft.Core

Classes

AccessPart

One placed part as the trace reads it.

AccessRiseCorrection

A mate rise the trace reads in place of the mate table's, for a part whose library data lost it. Only the trace reads it: the mate table, the magnet and the post rule keep the library's value.

AccessTrace

What the trace found in one structure.

AdaChart

The design team's ground-level events chart (2010 ADA Standards, section 240.2.1): elevated events to the ground-level events and types required, with the open last row's tail.

AdaChartRow

One row of the ground-level events chart.

AdaFigures

The five accessibility figures of one structure; each null when the file does not record it.

AdaHouseRules

The design team's house rules for counting play events. This is the one place the count asks, so the sheet, PBAUDIT and any later screen cannot disagree. None counts every part as the catalog and the design file code it (the legacy tool's own arithmetic).

AdaRequirement

What a structure's elevated events require.

AgeFit

One age band's suitability envelope for a catalog part: whether the part is appropriate for the band and, for elevated parts, the deck-height range it physically fits. min = max = 0 is the file's convention for ground-mounted and height-independent parts: ground level only once the structure's band is known, any height while it is not (see FitsHostHeight(IReadOnlyList<AgeFit>, double?, string?, string?)).

ArchScale

A standard architectural scale, "1/4" = 1'-0"".

AuditComponent

One placed component as the audit sees it — the neutral shape the Plugin harvests from ComponentScan so the rules stay AutoCAD-free (invariant 8).

AuditFinding

One thing the audit found.

AuditLimit

One rule's limit in inches, per age band, with the wiki card it came from.

AuditMate

One of a component's mate points, with what already sits on it.

AuditReport

What one audit pass produced: the findings, and an honest account of what could not be checked.

AuditRule

One PBAUDIT rule: its stable id, the finding kind it reports under, and what a finding asks.

AuditRuleBook

The design team's rulebook as data: the numeric limits, the part classification the limits are applied to, and the limb-climber catalog table. Read from data/audit/ (invariant 10's sidecar rule — the numbers are versioned with the code, never scattered as literals through src/), and every entry carries the wiki card it was transcribed from so a printed finding cites its source.

AuditRules

The register of PBAUDIT's rules (Design Studio lift, findings item 8). Each finding kind has one rule id that never changes and is never given to another rule, so a designer, a reviewer and the assistant can name a rule across versions. The action (what a finding asks for) is kept apart from the owner (who acts). The audit stays report-only: the action is advice, never a block.

BomCalculator

Pure BOM math. Descriptions come from the catalog cache when present, falling back to built-in labels for unenriched parts — never the network. Lives in Core so the tallying rules are unit-testable without AutoCAD; the Cad layer's only job is collecting PlacedComponents from the drawing.

BomCsv

Composes the priced, sectioned, per-level BOM as CSV text — the office file for sales, purchasing and the factory (execution plan Item 3). Pure text composition so the layout is unit-testable; the Cad layer owns the file write and its encoding (UTF-8 with BOM, so Excel detects it).

BomCsvResult

What Compose(string, IReadOnlyList<BomSection>, PricedBomResult, IReadOnlyList<PricedRow>, string, IEnumerable<string>, IReadOnlyList<(string Name, ColorSchedule Schedule)>?) produced: the file text plus the counts of what it actually rendered, so the command's report can describe the FILE rather than the flat tally it was built from (the same part at the same level in two structures is one flat row but two data rows here).

BomLine

A bill-of-materials line: one distinct part with its quantity.

BomLineRules

Which rule produced a bill-of-materials line, named with the reference build it follows - so a count the order desk disputes can be explained. Derived from the line's part number and description against the HardwareRules constants; every other line is a placed component.

BomSection

One section of a sectioned BOM: a play structure or a freestanding bucket, with the lines belonging to it. A quote prints these in order so no component is orphaned from the structure it belongs to.

BomWorkbook

Composes the priced BOM as an Excel workbook.

BomWorkbookInput

Everything the workbook is composed from.

BomWorkbookResult

What Compose(BomWorkbookInput) produced.

BomWorkbookUnit

One structure the workbook gives a tab: a named group, an xref, or the parts in no group.

BoxGrid

A uniform 2D hash grid over indexed boxes (bucketed by XY footprint; Z is checked in the exact intersection test). Same contract as PointGrid: the grid narrows candidates, and every match re-runs the exact Intersects(Box3) predicate — including its closed-interval touching-faces semantics — so results match a full O(n²) scan bit-for-bit.

CalloutBubble

A call-out bubble on the sheet.

CalloutKey

The call-out key's rows.

CalloutPart

One placed part as the call-outs see it.

CalloutPlacement

Where the bubbles go: each close to its own part, in open paper (off every stroke of line work, every other bubble, the north arrow and the deck height boxes), its leader short and ending on the part's line work. Every candidate spot round each target point is scored by its leader's length plus what the leader crosses: other parts' line work, its own part's, deck boxes, and (heaviest) other leaders. The most constrained bubble is placed first; then each bubble in turn is lifted and placed again against all the others until nothing improves. A bubble that still has no spot takes the nearest clear of the other bubbles and the boxes anywhere on the plan, over line work if it must (it is filled white, so its number still reads).

CalloutPlacementInput

What Place(IReadOnlyList<CalloutRequest>, IReadOnlyList<PlanStroke>, IReadOnlyList<SheetRect>, SheetRect) works from, as one value that can be saved and read back.

CalloutRequest

One bubble to place.

CalloutRow

One row of the call-out key.

CapAction

One step that brings the drawing's drawn caps to the posts. Pure data; the plugin performs it.

CapAction.Add

Draw a cap on a post.

CapAction.Delete

Erase a drawn cap no post wants: its post is gone, takes none, or already has one.

CapAction.Update

Move a drawn cap onto its post's top, or swap it for the other system's cap, keeping its handle.

CapPost

A post as the cap sync sees it.

CardStructure

The card's structure line (Item 37 H): which structure the selection is in, and the link that selects it.

CatalogFilter

Catalog compatibility rules, straight from the catalog file's own data: which parts fit a clicked host (MatesWith family + system type + the age envelopes' deck-height range) and which suit an age band.

CatalogFit

A "show me what fits this" context: the placed component a designer clicked, reduced to the three facts compatibility depends on.

CatalogLookup

One lookup response: cacheable parts, volatile prices, and misses.

CatalogNames

The flags the catalog writes at the end of a part's name. A trailing [Omit] marks a part the catalog keeps (it still prices and places) but does not offer first; the price list drops the same trailing flags from the names it shows (build/price-list-from-db.ps1).

CatalogPart

Catalog metadata for one part as returned by the catalog service — everything EXCEPT price. Price is volatile and is deliberately never cached into drawings; these fields are stable identity data that make a drawing self-describing offline.

CatalogPayload

Parses catalog lookup responses into CatalogLookup values, tolerating shape quirks in the feed.

CatalogQuery

A designer's search box text, parsed: the terms an entry must match and the terms that disqualify it. A term may be a bare word or a quoted phrase; the distinction is gone by the time it lands here, because both are matched the same way (as a contiguous substring).

CatalogSearch

The catalog search: how a designer's typing turns into a ranked list.

Three things the plain substring filter it replaces could not do. It ranks, so typing "deck" puts the square deck above the hundred parts whose DESCRIPTION happens to say "deck". It ignores punctuation in part numbers, so S-1101-R5, s1101r5 and 1101 all find the same deck. And when a query matches nothing at all it retries with a bounded edit distance, so one fat-fingered letter returns the part instead of an empty list — but only then, and it says so, because a fuzzy match that quietly displaces exact ones is worse than no match.

CatalogSearchResult

What a search found: the entries in relevance order, plus the near-miss term when nothing matched exactly and the search fell back to spelling tolerance. DidYouMean is non-null only in that case, so the palette can say the results are approximate instead of pretending.

CatalogSort

Sorting for the catalog palette. One rule is worth stating out loud: a part with no price sorts LAST whichever direction the price column is pointing. Ascending, an unpriced part is not "cheapest"; descending, it is not "most expensive". Missing data is missing data, and letting it win either end of the list is how a designer picks a part believing something the catalog never said.

CatalogVisibility
