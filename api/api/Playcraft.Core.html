Namespace Playcraft.Core

Classes

AgeFit

One age band's suitability envelope for a catalog part: whether the part is appropriate for the band and, for elevated parts, the deck-height range it physically fits. min = max = 0 is the file's convention for ground-mounted and height-independent parts: ground level only once the structure's band is known, any height while it is not (see FitsHostHeight(IReadOnlyList<AgeFit>, double?, string?, string?)).

AuditComponent

One placed component as the audit sees it — the neutral shape the Plugin harvests from ComponentScan so the rules stay AutoCAD-free (invariant 8).

AuditFinding

One thing the audit found.

AuditLimit

One rule's limit in inches, per age band, with the wiki card it came from.

AuditMate

One of a component's mate points, with what already sits on it.

AuditReport

What one audit pass produced: the findings, and an honest account of what could not be checked.

AuditRuleBook

The design team's rulebook as data: the numeric limits, the part classification the limits are applied to, and the limb-climber catalog table. Read from data/audit/ (invariant 10's sidecar rule — the numbers are versioned with the code, never scattered as literals through src/), and every entry carries the wiki card it was transcribed from so a printed finding cites its source.

BomCalculator

Pure BOM math. Descriptions come from the catalog cache when present, falling back to built-in labels for unenriched parts — never the network. Lives in Core so the tallying rules are unit-testable without AutoCAD; the Cad layer's only job is collecting PlacedComponents from the drawing.

BomCsv

Composes the priced, sectioned, per-level BOM as CSV text — the office file for sales, purchasing and the factory (execution plan Item 3). Pure text composition so the layout is unit-testable; the Cad layer owns the file write and its encoding (UTF-8 with BOM, so Excel detects it).

BomCsvResult

What Compose(string, IReadOnlyList<BomSection>, PricedBomResult, IReadOnlyList<PricedRow>, string, IEnumerable<string>) produced: the file text plus the counts of what it actually rendered, so the command's report can describe the FILE rather than the flat tally it was built from (the same part at the same level in two structures is one flat row but two data rows here).

BomLine

A bill-of-materials line: one distinct part with its quantity.

BomLineRules

Which rule produced a bill-of-materials line, named with the reference build it follows - so a count the order desk disputes can be explained. Derived from the line's part number and description against the HardwareRules constants; every other line is a placed component.

BomSection

One section of a sectioned BOM: a play structure or a freestanding bucket, with the lines belonging to it. A quote prints these in order so no component is orphaned from the structure it belongs to.

BoxGrid

A uniform 2D hash grid over indexed boxes (bucketed by XY footprint; Z is checked in the exact intersection test). Same contract as PointGrid: the grid narrows candidates, and every match re-runs the exact Intersects(Box3) predicate — including its closed-interval touching-faces semantics — so results match a full O(n²) scan bit-for-bit.

CatalogFilter

Catalog compatibility rules, straight from the catalog file's own data: which parts fit a clicked host (MatesWith family + system type + the age envelopes' deck-height range) and which suit an age band.

CatalogFit

A "show me what fits this" context: the placed component a designer clicked, reduced to the three facts compatibility depends on.

CatalogLookup

One lookup response: cacheable parts, volatile prices, and misses.

CatalogPart

Catalog metadata for one part as returned by the catalog service — everything EXCEPT price. Price is volatile and is deliberately never cached into drawings; these fields are stable identity data that make a drawing self-describing offline.

CatalogPayload

Parses catalog lookup responses into CatalogLookup values, tolerating shape quirks in the feed.

CatalogQuery

A designer's search box text, parsed: the terms an entry must match and the terms that disqualify it. A term may be a bare word or a quoted phrase; the distinction is gone by the time it lands here, because both are matched the same way (as a contiguous substring).

CatalogSearch

The catalog search: how a designer's typing turns into a ranked list.

Three things the plain substring filter it replaces could not do. It ranks, so typing "deck" puts the square deck above the hundred parts whose DESCRIPTION happens to say "deck". It ignores punctuation in part numbers, so S-1101-R5, s1101r5 and 1101 all find the same deck. And when a query matches nothing at all it retries with a bounded edit distance, so one fat-fingered letter returns the part instead of an empty list — but only then, and it says so, because a fuzzy match that quietly displaces exact ones is worse than no match.

CatalogSearchResult

What a search found: the entries in relevance order, plus the near-miss term when nothing matched exactly and the search fell back to spelling tolerance. DidYouMean is non-null only in that case, so the palette can say the results are approximate instead of pretending.

CatalogSort

Sorting for the catalog palette. One rule is worth stating out loud: a part with no price sorts LAST whichever direction the price column is pointing. Ascending, an unpriced part is not "cheapest"; descending, it is not "most expensive". Missing data is missing data, and letting it win either end of the list is how a designer picks a part believing something the catalog never said.

CollarBoxes

The collar model from a part's 3D drawing: one box per entity on a collar layer, in the 3D model's own frame, so the collar placement and counting that read the XAML models read the drawings unchanged.

CollarCounter

Collar counting. A collar is a physical clamp on a post; the component library models them as named meshes in each component's 3D art, so the count is derived from mesh bounding boxes: where two components share a post their collar boxes coincide and merge into one physical collar.

CollarModel

The collar meshes of one part's 3D model, by kind, in the model's own coordinates (X/Z horizontal plane, Y up).

CollarPlacement

Where a placed part's collars stand in the drawing — the half of the collar rule that comes before CollarCounter. The counter merges boxes that overlap; this decides where each part's boxes are, and a count is only as right as that.

CollarSources

Where a part's collars come from once the drawings are the library.

ComponentLibrary

The component catalog parsed from the library's ComponentData.xml: every entry, plus the library's own rule for which families are browsable. The file marks auto-inserted families (posts, fillers, caps) as omitted from the library tree; the browsable view honors that so designers see exactly the parts they are meant to place by hand.

ComponentTypes

The component TYPE tags written into each placed component's identity tag. Domain vocabulary shared by the Cad layer (which stores them as XData) and the BOM math here — the strings themselves are drawing data, so they must never change once drawings exist.

DeckHeightCheck

The verdict on a requested deck height, with the part's rated bounds so a refusal message can say what WOULD be accepted.

DeckHeightRule

The deck-height editing rule shared by every entry point that accepts a height (PBHEIGHT, PBSTAMP's prompt, the KCD importer's warning): heights live on the catalog's 6" grid, inside the 6" to 156" editing range, under the 108" cap for surface-mount decks, and inside the part's own age envelopes. A height that breaks a rule is refused with a named reason, never silently rewritten. The envelope semantic is FitsHostHeight(IReadOnlyList<AgeFit>, double?, string?, string?)'s: the structure's own age band when its design file names one, any appropriate band when it does not, and missing data never blocks, so the editing rule and the catalog fit filter can never disagree.

DeckJointPart

A placed part as the joint-hardware rules see it: deck-to-deck (DeckToDeckHardware) and erector-rock (ErectorRockHardware).

DeckToDeck

Which decks are physically attached: the adjacency behind structure membership (StructureGrouper). This is NOT the deck-to-deck hardware count, which joins only decks of one height at their mate points (DeckToDeckHardware); two decks at different heights sharing an edge are one structure but take no deck-to-deck set.

DeckToDeckHardware

The deck-to-deck hardware rule of the reference implementation: one set for every place where two decks of the same height meet at a mate point.

DependencyBinding

One resolved owner→dependent pairing in a design: which placed slide carries which placed sit-down wall/hood (or, generally, which owner carries which dependent), and how the two are linked.

DependencyCatalog

The owner→dependent auto-carry rule table, built from the component catalog's own AllowedAttachments declarations. An OWNER (a slide, a climber) names the dependent Categories it carries; a DEPENDENT (a sit-down wall/hood, a half/transition wall) carries the matching Category. This catalog resolves a placed component — keyed the way a design file names it, FileName then PartNumber — to those facts so DependencyPlanner can pair owners with the dependents they auto-carry.

DependencyFinding

One thing wrong with a design's dependency graph.

DependencyPlan

The complete dependency picture for a design: every resolved owner→dependent binding, plus every issue (missing, broken, orphaned, inconsistent). A command reconciles a drawing against it, and a MOVE/DELETE of an owner reads DependentIdsOf(string) to carry its dependents.

DependencyPlanner

The dependency pass over a whole design: pairs every owner (slide, climber) with the dependents it auto-carries (sit-down wall/hood, half/transition wall) and reports the graph's gaps. Pure and vault-independent — the drawing analogue of FillerPlanner, but driven by the design file's own attachment links rather than deck geometry.

DependencyTally

The headline numbers of a DependencyPlan, counted once so a reporting command never has to derive them (and never double-counts a single drifted pair, which both InconsistentLink emitters would otherwise invite: Pass 1 anchors the finding on the dependent, Pass 2 on the owner, but each still describes exactly one binding).

DependentChoice

The catalog parts an owner could carry, and whether the choice is the designer's to make. Placement asks this before it asks the designer: a slide whose sit-down wall is determined needs no prompt, a climber with four themed half walls does.

DependentPairing

Item 15, "pairing comes from positions too": which owner (a slide, a climber) a dependent (a sit-down wall, a half wall) belongs to, decided by where the two sit, so a wall placed by hand pairs exactly as one the plugin placed.

DependentSelector

Which catalog parts satisfy an owner's AllowedAttachments for a given structure. The rule table (DependencyCatalog) says WHAT categories an owner carries; this says WHICH parts can fill them here, which is what a placement command needs before it can carry anything.

DesignAudit

The design team's geometry rules as predicates (execution plan Item 10). Report only, forever by default: nothing here moves, refuses or repairs anything. The rule is the designer's to overrule.

DesignAuditRecord

A review record: who reviewed which content, when.

DesignBomLine

One bill-of-materials line with the rule that produced it.

DesignCompliance

A structure's compliance values.

DesignDocument

The suite's own record of a design (Item 22): what the drawing holds, structure by structure, with every bill-of-materials line and the rule that made it, compliance values with their provenance, prices with their source, review records keyed on a content hash, and the link to the legacy design file written beside it. The legacy file is a projection of this document. Serialized by DesignDocumentWriter, read back by DesignDocumentReader, validated by DesignDocumentSchema.

DesignDocumentBuilder

Builds the design document an export writes: parts in the drawing's world frame with position-based keys, every bill-of-materials line with its rule, the counts the legacy tab records, compliance values with their rules, prices per structure, and audit records carried forward.

DesignDocumentReader

Reads a DesignDocument back from JSON, strictly: the text is validated against DesignDocumentSchema first, and anything the schema refuses is refused here with the failing path named. Also projects a document onto the legacy model (ToKcdDesign(DesignDocument)), so every command that reads a legacy design file can read a document instead.

DesignDocumentSchema

The design document's JSON Schema (2020-12), embedded in this assembly from data/schema/design.schema.json so every caller validates against the same file with nothing to configure.

DesignDocumentWriter

Writes a DesignDocument as JSON: camelCase, indented with two spaces and line feeds, every field in a fixed order, real numbers and booleans, null for unknown. The same document always serializes to the same bytes on every platform.

DesignEnvelope

The document's envelope.

DesignExportInput

Everything one export hands to Build(DesignExportInput).

DesignExportStructure

One structure as an export hands it to DesignDocumentBuilder: the legacy tab it wrote (re-read from the written file) plus what only the drawing knows about it.

DesignExtraHardware

The extra-hardware band decision for one play structure.

DesignFrame

The legacy canvas frame: canvas = (x + shift.x, -(y + shift.y)) for a world position (x, y). The shift is zero for a design imported from a legacy file (import places parts at the file's own coordinates, Y-flipped) and the canvas-centering translation for a design the New export authored.

DesignHardwareCounts

The hardware counts a structure's legacy tab records; null where it records none.

DesignHashes

The document's content hashes. Formatting of the JSON never affects one.

DesignKeys

Part identity across tools: position and name, never a GUID a reader may renew. The same rendering the legacy writer's content comparison uses, so a change the writer counts is a change the document's hash counts.

DesignLegacy

The link to the legacy design file.

DesignLegacyTab

One structure's legacy tab.

DesignPart

One part of a structure.

DesignPricedStructure

One structure's prices.

DesignPricing

The document's prices.

DesignRuledValue

A value with the rule it came from; a null value is honestly unknown.

DesignSchemaError

One way a document fails its schema.

DesignSchemaResult

What validating a document against its schema found.

DesignSettings

What a structure declares about itself.

DesignStructure

One structure: a designer's named group, written as one legacy design tab.

DesignUnassigned

A component the export could see and did not write.

DwgMarker

One insert a part drawing holds, in the drawing's model-space frame (inches).

DwgPolyline

One polyline run a part drawing holds (lines, arcs and circles arrive as runs too), model space.

DwgSolidBox

The bounds of one entity of a part's 3D drawing, in the drawing's own frame (Z up).

ElevationDrift

Whether an edit that moved a part in Z left the drawing disagreeing with itself — the rule behind the OSNAPZ trap.

EnvFile

Line-level editing for the suite's per-user settings files: plain text, one KEY="value" per line, # comments. Editing works on lines rather than a parsed model on purpose — a settings file may hold keys and comments this code has never heard of, and a save must let them all through untouched.

ErectorRockHardware

The erector-rock hardware rule of the reference implementation: one set of ErectorRockPart for every pair of erector rocks joined end to end.

ExistingPost

A post already in the drawing, as the reconciler sees it.

ExtraHardware

The extra-hardware allowance (HS-1007): a priced number of spare-hardware sets per play structure, banded on what the structure costs.

ExtraHardwareBand

What the band rule decided for one structure.

FallHeightAndCapacity

A structure's maximum fall height and child capacity, with the parts that had no catalog facts to contribute (both values may then be low).

FallHeightRule

The maximum fall height and child capacity of one structure, from its parts' catalog facts. A part's fall height is its catalog fall height plus its adjustment; when the catalog gives the fall height as "AUTO" it is the part's placed design height plus the adjustment instead. The structure's maximum is the largest of its parts' and never below 0. Its child capacity is each part's capacity times the copies the placement stands for, summed. Fall height stays a fact of its own: only an "AUTO" part derives it from the placed height, and nothing writes it back into the instance height.

FeatureCatalog

Strict loader for data/features.json. Anything the schema forbids — missing fields, malformed command names, duplicate commands — throws FormatException rather than degrading silently, because two consumers (palette and docs) would otherwise drift apart in different ways.

FeatureDefinition

One user-facing plugin feature as declared in data/features.json — the single source of truth consumed by BOTH the AutoCAD palette and the documentation site's End-User tab. Mirrors data/features.schema.json.

FillerCatalog

The filler catalog parsed from the library's FillerData.xml: the per-system dimension tables the selection rule searches, the swap groups behind the "swap filler" UI, and the global 6-inch-gap flag.

FillerDeck

One deck-like component as the filler pass sees it, all geometry in world drawing coordinates (Y up, inches).

FillerEntry

One filler part's dimension entry from the library's FillerData.xml.

FillerPlacement

One filler the plan wants standing in the drawing.

FillerPlan

The complete filler plan for a drawing: where fillers belong and where any existing filler must go away (flush joints and suppressed 6" steps).

FillerPlanner

The filler pass over a whole drawing: pairs the deck-like components the legacy way (shared posts + coincident mate points) and folds the per-point decisions of DecideAtMatePoint(FillerCatalog, string, int, MateLengthClass) into one position-keyed plan a command can reconcile the drawing against.

FillerSelector

Filler auto-selection: the legacy engine's exact lookup and trigger rules, ported as pure functions (see docs/pd-parity.md). A filler is a vertical spacer bridging the height step where two mated decks of different DesignHeights meet on shared posts — one per shared mate point per height-differing deck pair. It is NOT emitted on open perimeter edges. The legacy trigger pairs decks hanging off a common post that share at least two posts and coincident mate points, then decides per shared mate point as DecideAtMatePoint(FillerCatalog, string, int, MateLengthClass) does.

FootprintStackRule

The stacking half of the magnet: a deck clicked ON another deck's footprint is born at that deck's exact plan position instead of at the raw pick, so a tower can be dragged instead of typed.

FreestandingSections

Quote sections for components a designer left outside every group. The bucket names come from the component library's own family vocabulary, which the bundled price list repeats verbatim, so they resolve with no vault and no network.

HardwareCalculator

Builds the counted-hardware BOM lines from design tallies.

HardwareRules

Counted-hardware rules: the BOM lines that are tallies of the design rather than placed components — collars, post caps, deck-to-deck and erector-rock hardware, and the price-banded extra-hardware allowance. Part numbers and system-type mappings are ports of the legacy BOM output rules, verified against the current price list.

HeightLabel

The height attribute's value format — the one string that is BOTH the designer-visible label and the canonical stored height (ADR §4.4a: the attribute owns height, there is no second copy). Because storage and display are the same string, Format(double) must round-trip every height the suite handles: "0.####" keeps a hand-edited 40.25" exact where the old display-only "0.#" would have stored it back as 40.3".

HeightResolver

Height resolution for placement flows (F-032): what height metadata a placement should carry, and whether a part is rated for the host height it snapped to. Pure functions over catalog data, shared by the magnetic placement jig and the catalog fit filter so the two can never disagree about what "fits at this height" means.

KcdAttachmentPoint

One attachment point of a component in a legacy design file. In the file these are FLAT repeatable <AttachmentPoints> elements with the fields as direct children — there is no per-point wrapper element.

KcdComponent

One placed component in a legacy design file.

KcdComponentAddition

A component that exists in the drawing but not in the design file — placed with the suite's own commands — to be written into the exported tab.

KcdComponentUpdate

One component's placement as it now stands in the drawing.

KcdCountGaps

What the drawing could not count for a tab, so that a count it gives may be low: parts whose 3D model is missing from the library (their collars are unseen) and parts the price list does not price (their cost is missing from the extra-hardware subtotal).

KcdDesign

A legacy design file parsed into a pure model.

KcdDesignTab

One design tab (structure) in a legacy design file.

KcdExportRefusedException

The export refused to write anything: a design height that is not a whole number of inches. The order system reads every DesignHeight as a whole number and, meeting one that is not, stops loading the whole file without a message - so a fractional height must never leave the suite.

KcdHardwareCounts

The hardware counts a design tab records for ordering. The order system prices exactly these numbers as written - it recounts none of them except an R3.5 collar count of zero - so they have to be true when the file leaves the suite.

KcdHeights

Design heights as the file must carry them: whole inches.

KcdLayerAudit

Layer-vs-geometry disagreement report for an imported design file (ADR §4.4c's deferred import half). The legacy app cannot run this check on itself — a 2D canvas has no answer to "what stands on what" — so the designer's hand-typed tiers go unexamined until the texted top view splits into unreadable pages. The suite derives the storeys and can say where the file's own numbers contradict them.

This is a REPORT, never a correction: adoption of the file's numbering — including a privately inverted one — is the §4.4c rule, so the audit compares the PARTITION, not the labels. A walkable band wholly labeled 3 is consistent; a band split between two labels is not. On the reference corpus (11 files, 113 decks) the checks flag nothing, so a finding on a real file is signal, not noise.

KcdLayerAuditResult

What Of(IReadOnlyList<KcdComponent>, Func<KcdComponent, bool>) found in one design tab.

KcdLayerDisagreement

One place a design file's hand-typed Layer disagrees with its own geometry. Kind is a stable machine word for tests and grouping; Detail is the sentence a command prints.

KcdLayers

Layer (storey/tier) assignment for components added to a design file (ADR §4.4c). The file's <Layer> integer is the legacy designer's hand-typed storey index — it filters the build in the Layer Manager and splits the texted top-view PDF into one page per tier. The legacy app cannot compute it (a 2D canvas has no answer to "what stands on what"), so designers maintain it by hand; the suite can, so additions derive their tier and an existing component's Layer is treated as designer evidence that is never rewritten and never "corrected".

Corpus-measured before writing (reference kcds, 9 multi-layer tabs, 128 deck placements): designer layers are clean non-interleaving height bands 9/9; the traversal tier below reproduces 102/128 hand assignments, and the misses are one file with privately inverted numbering (adoption keeps it) and tiers reached only by climbing links (adoption inherits them from the file's own bands). Height ALONE cannot draw the band line — the corpus holds a between-band gap equal to the largest within-band step (both 24") — which is why adjacency and footprint coincidence participate.

The one way into the component library's files (Global Invariant 10: the library is read-only in every respect). Every path the suite builds into the library comes from here, and every read here opens the file for reading only, sharing it with anyone else. Nothing here, or anywhere else in src, opens a library file for writing; a source-discipline test holds that line.

VaultFootingPoint

A component footing point: where it meets the ground and the footing it takes.

VaultInventory

Inspects a component-library root without assuming which of the two known layouts it is: the development tree keeps the family folders under {root}\library with the data files at the root, while a designer pointing PBVAULT at their own library usually names the family-folder level directly (…\Access Components\S0-1291\…) with the data files at that level or one above. Everything here is inspection only — no caching, no AutoCAD — so the plugin can describe a path BEFORE committing to it.

VaultMatePoint

A component mate point: where another component attaches and which way it faces.

VaultPolyline

One connected polyline run: vertices with AutoCAD-style bulges (bulge[i] curves the segment from vertex i to i+1; tan(sweep/4)).

VaultSvgParser

Minimal parser for the component library's machine-generated SVGs. They use a constrained vocabulary: a JSON metadata block (insertion point, post slots, mate points) and path elements using only absolute M/L/A/Z commands. Anything outside that vocabulary throws — callers fall back to placeholder geometry rather than render a wrong shape.

VaultXamlParser

Parser for the component library's native 2D geometry files — the legacy designer's own Component2D XAML ("{folder}.xaml"), the format the recovered library actually ships. It carries the same attachment metadata a design file's placed component does: the insertion point, the post slots (with their height offsets, and the Revolution slots some parts add), the mate points (with their length class and mate-type), the footing points, the attachment points, and the file's own part number, revision and design height — everything the library sidecar migrates from it. Produces the same VaultComponent contract as VaultSvgParser, so every downstream consumer (block build, filler pairing, mate snap) is source-agnostic.

Xaml3DAssets

Filename preference for the library's exported 3D models ("{folder}-3D.xaml"). Pure string work so the tolerance rules are testable: the vault is hand-maintained and its known misnamings — a "-3D2" suffix, a "-3D_NEW" variant, two parts' files sharing one misfiled folder — must resolve to the right model instead of silently dropping the part.

Xaml3DMeshes

Minimal reader for the component library's exported 3D XAML models. It extracts collar mesh bounding boxes — the input to CollarCounter — by scanning MeshGeometry3D resources whose key starts with Collar_ (case-insensitive across the library's old COLLAR_ and current Collar_ conventions; CollarHW_ is hardware, not a collar, and never matches because of the underscore), and the R3.5 collars keyed KCR35_. Pure text parsing — no WPF — so it runs and tests headlessly.
