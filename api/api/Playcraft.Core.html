Namespace Playcraft.Core

Classes

AgeFit

One age band's suitability envelope for a catalog part: whether the part is appropriate for the band and, for elevated parts, the deck-height range it physically fits (min = max = 0 means any height — the file's convention for ground-mounted and height-independent parts).

BomCalculator

Pure BOM math. Descriptions come from the catalog cache when present, falling back to built-in labels for unenriched parts — never the network. Lives in Core so the tallying rules are unit-testable without AutoCAD; the Cad layer's only job is collecting PlacedComponents from the drawing.

BomCsv

Composes the priced, sectioned, per-level BOM as CSV text — the office file for sales, purchasing and the factory (execution plan Item 3). Pure text composition so the layout is unit-testable; the Cad layer owns the file write and its encoding (UTF-8 with BOM, so Excel detects it).

BomCsvResult

What Compose(string, IReadOnlyList<BomSection>, PricedBomResult, PricedRow?, string, IEnumerable<string>) produced: the file text plus the counts of what it actually rendered, so the command's report can describe the FILE rather than the flat tally it was built from (the same part at the same level in two structures is one flat row but two data rows here).

BomLine

A bill-of-materials line: one distinct part with its quantity.

BomSection

One section of a sectioned BOM: a play structure or a freestanding bucket, with the lines belonging to it. A quote prints these in order so no component is orphaned from the structure it belongs to.

BoxGrid

A uniform 2D hash grid over indexed boxes (bucketed by XY footprint; Z is checked in the exact intersection test). Same contract as PointGrid: the grid narrows candidates, and every match re-runs the exact Intersects(Box3) predicate — including its closed-interval touching-faces semantics — so results match a full O(n²) scan bit-for-bit.

CatalogFilter

Catalog compatibility rules, straight from the catalog file's own data: which parts fit a clicked host (MatesWith family + system type + the age envelopes' deck-height range) and which suit an age band.

CatalogFit

A "show me what fits this" context: the placed component a designer clicked, reduced to the three facts compatibility depends on.

CatalogLookup

One lookup response: cacheable parts, volatile prices, and misses.

CatalogPart

Catalog metadata for one part as returned by the catalog service — everything EXCEPT price. Price is volatile and is deliberately never cached into drawings; these fields are stable identity data that make a drawing self-describing offline.

CatalogPayload

Parses catalog lookup responses into CatalogLookup values, tolerating shape quirks in the feed.

CollarCounter

Collar counting. A collar is a physical clamp on a post; the component library models them as named meshes in each component's 3D art, so the count is derived from mesh bounding boxes: where two components share a post their collar boxes coincide and merge into one physical collar.

ComponentLibrary

The component catalog parsed from the library's ComponentData.xml: every entry, plus the library's own rule for which families are browsable. The file marks auto-inserted families (posts, fillers, caps) as omitted from the library tree; the browsable view honors that so designers see exactly the parts they are meant to place by hand.

ComponentTypes

The component TYPE tags written into each placed component's identity tag. Domain vocabulary shared by the Cad layer (which stores them as XData) and the BOM math here — the strings themselves are drawing data, so they must never change once drawings exist.

DeckHeightCheck

The verdict on a requested deck height, with the part's rated bounds so a refusal message can say what WOULD be accepted.

DeckHeightRule

The deck-height editing rule shared by every entry point that accepts a height (PBHEIGHT, PBSTAMP's prompt, the KCD importer's warning): heights live on the catalog's 6" grid, inside the 6" to 156" editing range, under the 108" cap for surface-mount decks, and inside the part's own age envelopes. A height that breaks a rule is refused with a named reason, never silently rewritten. The envelope semantic is FitsHostHeight(IReadOnlyList<AgeFit>, double?)'s: any appropriate band covers the height, 0/0 means any, and missing data never blocks, so the editing rule and the catalog fit filter can never disagree.

DeckToDeck

Deck-to-deck attachment counting for the HS-1100-2 hardware line.

DependencyBinding

One resolved owner→dependent pairing in a design: which placed slide carries which placed sit-down wall/hood (or, generally, which owner carries which dependent), and how the two are linked.

DependencyCatalog

The owner→dependent auto-carry rule table, built from the component catalog's own AllowedAttachments declarations. An OWNER (a slide, a climber) names the dependent Categories it carries; a DEPENDENT (a sit-down wall/hood, a half/transition wall) carries the matching Category. This catalog resolves a placed component — keyed the way a design file names it, FileName then PartNumber — to those facts so DependencyPlanner can pair owners with the dependents they auto-carry.

DependencyFinding

One thing wrong with a design's dependency graph.

DependencyPlan

The complete dependency picture for a design: every resolved owner→dependent binding, plus every issue (missing, broken, orphaned, inconsistent). A command reconciles a drawing against it, and a MOVE/DELETE of an owner reads DependentIdsOf(string) to carry its dependents.

DependencyPlanner

The dependency pass over a whole design: pairs every owner (slide, climber) with the dependents it auto-carries (sit-down wall/hood, half/transition wall) and reports the graph's gaps. Pure and vault-independent — the drawing analogue of FillerPlanner, but driven by the design file's own attachment links rather than deck geometry.

DependencyTally

The headline numbers of a DependencyPlan, counted once so a reporting command never has to derive them (and never double-counts a single drifted pair, which both InconsistentLink emitters would otherwise invite: Pass 1 anchors the finding on the dependent, Pass 2 on the owner, but each still describes exactly one binding).

DependentChoice

The catalog parts an owner could carry, and whether the choice is the designer's to make. Placement asks this before it asks the designer: a slide whose sit-down wall is determined needs no prompt, a climber with four themed half walls does.

DependentSelector

Which catalog parts satisfy an owner's AllowedAttachments for a given structure. The rule table (DependencyCatalog) says WHAT categories an owner carries; this says WHICH parts can fill them here, which is what a placement command needs before it can carry anything.

EnvFile

Line-level editing for the suite's per-user settings files: plain text, one KEY="value" per line, # comments. Editing works on lines rather than a parsed model on purpose — a settings file may hold keys and comments this code has never heard of, and a save must let them all through untouched.

FeatureCatalog

Strict loader for data/features.json. Anything the schema forbids — missing fields, malformed command names, duplicate commands — throws FormatException rather than degrading silently, because two consumers (palette and docs) would otherwise drift apart in different ways.

FeatureDefinition

One user-facing plugin feature as declared in data/features.json — the single source of truth consumed by BOTH the AutoCAD palette and the documentation site's End-User tab. Mirrors data/features.schema.json.

FillerCatalog

The filler catalog parsed from the library's FillerData.xml: the per-system dimension tables the selection rule searches, the swap groups behind the "swap filler" UI, and the global 6-inch-gap flag.

FillerDeck

One deck-like component as the filler pass sees it, all geometry in world drawing coordinates (Y up, inches).

FillerEntry

One filler part's dimension entry from the library's FillerData.xml.

FillerPlacement

One filler the plan wants standing in the drawing.

FillerPlan

The complete filler plan for a drawing: where fillers belong and where any existing filler must go away (flush joints and suppressed 6" steps).

FillerPlanner

The filler pass over a whole drawing: pairs the deck-like components the legacy way (shared posts + coincident mate points) and folds the per-point decisions of DecideAtMatePoint(FillerCatalog, string, int, MateLengthClass) into one position-keyed plan a command can reconcile the drawing against.

FillerSelector

Filler auto-selection: the legacy engine's exact lookup and trigger rules, ported as pure functions (see docs/pd-parity.md). A filler is a vertical spacer bridging the height step where two mated decks of different DesignHeights meet on shared posts — one per shared mate point per height-differing deck pair. It is NOT emitted on open perimeter edges. The legacy trigger pairs decks hanging off a common post that share at least two posts and coincident mate points, then decides per shared mate point as DecideAtMatePoint(FillerCatalog, string, int, MateLengthClass) does.

FootprintStackRule

The stacking half of the magnet: a deck clicked ON another deck's footprint is born at that deck's exact plan position instead of at the raw pick, so a tower can be dragged instead of typed.

FreestandingSections

Quote sections for components a designer left outside every group. The bucket names come from the component library's own family vocabulary, which the bundled price list repeats verbatim, so they resolve with no vault and no network.

HardwareCalculator

Builds the counted-hardware BOM lines from design tallies.

HardwareRules

Counted-hardware rules: the BOM lines that are tallies of the design rather than placed components — collars, post caps, deck-to-deck hardware, and the price-banded extra-hardware allowance. Part numbers and system-type mappings are ports of the legacy BOM output rules, verified against the current price list.

HeightLabel

The height attribute's value format — the one string that is BOTH the designer-visible label and the canonical stored height (ADR §4.4a: the attribute owns height, there is no second copy). Because storage and display are the same string, Format(double) must round-trip every height the suite handles: "0.####" keeps a hand-edited 40.25" exact where the old display-only "0.#" would have stored it back as 40.3".

HeightResolver

Height resolution for placement flows (F-032): what height metadata a placement should carry, and whether a part is rated for the host height it snapped to. Pure functions over catalog data, shared by the magnetic placement jig and the catalog fit filter so the two can never disagree about what "fits at this height" means.

KcdAttachmentPoint

One attachment point of a component in a legacy design file. In the file these are FLAT repeatable <AttachmentPoints> elements with the fields as direct children — there is no per-point wrapper element.

KcdComponent

One placed component in a legacy design file.

KcdComponentAddition

A component that exists in the drawing but not in the design file — placed with the suite's own commands — to be written into the exported tab.

KcdComponentUpdate

One component's placement as it now stands in the drawing.

KcdDesign

A legacy design file parsed into a pure model.

KcdDesignTab

One design tab (structure) in a legacy design file.

KcdJson

The modern wire format for a design (F-030 companion): a versioned, camelCase, UTF-8 JSON document with real numbers and booleans, explicit units (including the legacy feet/inches per-container quirk, spelled out per slot), ISO 8601 timestamps, and stable field order. Content-complete against the parsed model — RenderTransform rides along verbatim — so the .kcd stays the backwards-compatible interchange while anything modern consumes this instead of XML.

KcdJsonMeta

Provenance stamped into a JSON export.

KcdLayerAudit

Layer-vs-geometry disagreement report for an imported design file (ADR §4.4c's deferred import half). The legacy app cannot run this check on itself — a 2D canvas has no answer to "what stands on what" — so the designer's hand-typed tiers go unexamined until the texted top view splits into unreadable pages. The suite derives the storeys and can say where the file's own numbers contradict them.

This is a REPORT, never a correction: adoption of the file's numbering — including a privately inverted one — is the §4.4c rule, so the audit compares the PARTITION, not the labels. A walkable band wholly labeled 3 is consistent; a band split between two labels is not. On the reference corpus (11 files, 113 decks) the checks flag nothing, so a finding on a real file is signal, not noise.

KcdLayerAuditResult

What Of(IReadOnlyList<KcdComponent>, Func<KcdComponent, bool>) found in one design tab.

KcdLayerDisagreement

One place a design file's hand-typed Layer disagrees with its own geometry. Kind is a stable machine word for tests and grouping; Detail is the sentence a command prints.

KcdLayers

Layer (storey/tier) assignment for components added to a design file (ADR §4.4c). The file's <Layer> integer is the legacy designer's hand-typed storey index — it filters the build in the Layer Manager and splits the texted top-view PDF into one page per tier. The legacy app cannot compute it (a 2D canvas has no answer to "what stands on what"), so designers maintain it by hand; the suite can, so additions derive their tier and an existing component's Layer is treated as designer evidence that is never rewritten and never "corrected".

Corpus-measured before writing (reference kcds, 9 multi-layer tabs, 128 deck placements): designer layers are clean non-interleaving height bands 9/9; the traversal tier below reproduces 102/128 hand assignments, and the misses are one file with privately inverted numbering (adoption keeps it) and tiers reached only by climbing links (adoption inherits them from the file's own bands). Height ALONE cannot draw the band line — the corpus holds a between-band gap equal to the largest within-band step (both 24") — which is why adjacency and footprint coincidence participate.

KcdLink

One owner→dependent pairing to write into a design file: a placed slide and the sit-down wall it carries. Reconciling a link writes BOTH directions — the owner's attachment slot (authoritative) and the dependent's back-reference — so the pair never lands in the one-way state InconsistentLink reports.

KcdMatePoint

One mate point of a component in a legacy design file.

KcdNewFile

New-design skeleton for F-035: a complete, empty legacy design file that ApplyPlacements(string, string, IReadOnlyList<KcdComponentUpdate>, IReadOnlyCollection<string>, IReadOnlyList<KcdComponentAddition>?, IReadOnlyList<KcdLink>?) can then pour components into — so a from-scratch drawing exports through the exact corpus-pinned writer the read-modify-write path uses, never a second component serializer.

The legacy app cannot be run here, so the envelope is deliberately a compatibility superset of the available evidence (the corpus and the legacy loader; citations in the source comments): the loader's hard requirements, the newest corpus writer's shape, both underlay forms, a complete production color scheme (an incomplete one opens but blocks saving in the legacy app), zeroed counts (the legacy app recomputes them on open), and the legacy writer's own empty-thumbnail fallback.

KcdNewPostSlot

A post slot of a component being added to a design file.

KcdPlacement

The design-canvas placement rule for legacy design files (F-029), verified against the demo/KCD corpus: slots on different components that share a PostID land on one world point under exactly this transform (sub-0.14" agreement; see KcdPlacementTests).

KcdPostIds

Post-identity assignment for components added to a design file. A slot's PostID is the file's identity for a physical post: slots on different components sharing an id are one post, and the design's post count is the number of distinct ids. New slots therefore inherit the id of any post they land on and mint fresh ids otherwise.

KcdPostReconciliation

A design tab's post ids resolved against its own components. A slot's PostID has two meanings the legacy format never separates: most name a placed component (an insertable, surface-mount or Revolution post — the component IS the post), and the rest are abstract identities for posts that exist only as shared bookkeeping between deck corners. Counting the two as one number is what made real designs look wrong: a file whose every post is a placed component "declares" as many ids as it has post components, and comparing that against a geometric slot merge measures nothing. This record separates them so each part can be judged by the rule that actually applies to it.

KcdPostSlot

One post slot a component provides in a legacy design file.

KcdReader

Reader for the legacy designer's project files (F-028). Parses the design structure — tabs, component placements, posts, attachments, mates — into a pure model; elements outside that structure are ignored (the exporter, F-030, will preserve them by read-modify-write on the original text).

KcdWriteResult

What ApplyPlacements(string, string, IReadOnlyList<KcdComponentUpdate>, IReadOnlyCollection<string>, IReadOnlyList<KcdComponentAddition>?, IReadOnlyList<KcdLink>?) did.

KcdWriter

Exporter for legacy design files (F-030): read-modify-write with preservation, the pattern the production web platform proved (KcdModel::updateProjectProperties). Only the slice the drawing owns — component placements and deletions in one tab — is touched; every other byte, including unknown or newer elements (Flag, MeshColors, POV, DesignLock), passes through opaquely. Not byte-exact by design, but components that didn't move keep their original text verbatim.

LibraryEntry

One catalog entry a designer can browse and place.

MateCandidateSet

The shared candidate-set primitive behind every mate-point consumer — the click path builds one per click, the F-032 jig builds one per jig start and queries it per cursor sample, and the F-033 osnap overrule shares WorldMatePoints(IReadOnlyList<MatePointRecord>, Transform2) for its per-entity variant. Precomputes every component's world-space mate points and a PointGrid over the occupancy positions; ForChild(MatePointRecord) adds a per-child grid over the compatible host points. The grids only narrow candidates: every returned match re-runs the exact per-host predicates of the original scan (CompatiblePoints(IReadOnlyList<MatePointRecord>, string, string, string, string, string, MateRules) plus Choose(IReadOnlyList<SnapPoint>, IReadOnlyList<Pt>, Pt, double, double)'s closed-interval distance rules), so answers are bit-identical to FindSnapReference(MatePointRecord, Pt, double, double), the retained O(n²) oracle — the differential tests hold this to account.

MateComponent

One placed component as the mate search sees it: its catalog mate table, its world transform, and the two roles it can play — snap host (offering mate points to capture) and occupier (its own mates, or its insertion point when it has none, mark nearby host points as taken). Posts play neither role: they live on corner slots, not mate points.

MateHarvest

Reads a component library's mate points straight off disk, so the plugin can use the library the designer actually has instead of only the table baked in at build time (build/build-mate-table.ps1 produces the same rows from the same files — MateHarvestEquivalenceTests holds the two to account).

This walks thousands of folders and must never run on a UI thread or inside an osnap/jig hot path (the F-033 rule); callers harvest once, off-thread, and swap the finished table in.

MateHarvestResult

What a harvest of a component library turned up: the mate rows, which components were readable, and what went wrong — enough for the caller to report the result honestly instead of silently shipping a partial table.

MateMarker

One mate point rendered for a designer to look at: where it is, and whether something already sits on it.

MateMatcher

F-019 compatibility gate: which of a host's mate points a given child part may legally take. Type pairing and family restrictions come from MateRules; the tri-deck / half-deck component exclusions apply only when the host is one of the legacy engine's hard-coded special decks.

MatePlacement

The placement math shared by every mate consumer: the exact insertion point and rotation that land a child part's mate connector on a captured host point with the mate vectors opposing.

MatePointRecord

One mate point of a catalog part from the canonical mate table (data/mates/mate-points.csv, generated by build/build-mate-table.ps1). Geometry and type attributes both come from the library component XAML's MatePoints block — verified 1:1 against the engineering DWGs' mate marker blocks on every part the earlier DWG-join table covered.

MateQueryResult

A mate search answer across every host in the drawing: the aggregate outcome plus, when snapped, the winning host and its captured point.

MateRules

Mate-type compatibility rules and component exclusion lists from the library's rule file (data/mates/mate-rules.json, generated by build/build-mate-table.ps1 from MateTypeRules.xml). All lookups are case-insensitive because the library's own labels are not consistently cased (e.g. "default", "Default", and "DEFAULT" all occur).

MateSnapQuery

A mate search bound to one child part. Construction resolves compatibility per host and indexes the compatible world points in a PointGrid; Find(Pt, double, double) then answers from the pick's neighborhood only, re-running the exact distance and occupancy predicates of the per-host scan so the answer matches FindSnapReference(MatePointRecord, Pt, double, double) bit-for-bit.

MateTable

The canonical per-part mate table: every mate point of every component in the library, keyed by part name (case-insensitive).

PlacedComponent

One placed component as the BOM sees it: the identity-tag fields plus the catalog display name when the drawing has one cached. This is the neutral shape the Cad layer maps AutoCAD block references into — Core never sees an AutoCAD type.

Placement3D

Where a component's 3D model sits in world space.

PointGrid

A uniform 2D hash grid over indexed points — the O(1)-per-query replacement for "scan every point" proximity loops. Callers add points with their own indices and query for entries strictly within a tolerance, which is the coincidence predicate every ported legacy rule uses (see PdTolerance). The grid only narrows the candidate set; every returned match re-checks the exact same DistanceTo(Pt) comparison the O(n²) scans use, so results are bit-identical to a full scan — the differential tests in Playcraft.Core.Tests hold this to account.

PointSnapper

F-019 capture rule: the nearest declared mate point within a Euclidean radius of the pick wins; points that already have a child sitting on them are skipped in the nearest-search. The radius replicates the legacy engine; the occupancy skip is the suite's own addition — see the constants. Pure math — the plugin transforms points to world space and harvests occupied positions before calling in.

PostFamilies

Which catalog families ARE posts — parts that stand a vertical structural post in their own right when placed as a component. Production designs are built this way: the 2026-08-04 corpus measurement found six of the seven harness design tabs resolve EVERY distinct PostID to a placed component in one of these families (the seventh, R507312CA, resolves four of six), so a component in a post family standing on a deck corner is that corner's post, and anything that counts or mints posts must treat it as one.

PostMerge

Post-coincidence math: collapses deck corner slots into shared physical posts.

PostNumberFormatter

Post part-number math. The catalog encodes a deck-height post as a whole-foot stock post factory-cut for that deck: S-10{H:00}-{SYS}F-{N}-{deck:000}-{top:000} where top is the post top above grade (deck height + 39" rail for in-ground, + 3" for surface mount), H = ceil(top / 12) is the stock length in feet, and N = H*12 - top is the cut-down in inches. Surface mount appends -SM. Derived from and verified against the full price list (every fractional post row follows this encoding exactly).

PostPlanner

Height-aware post planning: merges deck corner slots into physical posts with PostMerge's exact adopt-first coincidence rule, and gives each post the maximum height of the slots it absorbed — a shared post must serve its tallest deck.

PostSpec

A resolved support post: full catalog part number plus its geometry facts.

PriceBook

The offline price list: part number → MSRP/REP prices, loaded from the bundled CSV export of the company price workbook. Lookup is case-insensitive; duplicate part numbers keep the first row (the workbook lists one row per product NAME, so a part can appear several times at the same price).

PriceEntry

One price-book entry: a part with its retail (MSRP) and discounted (REP) price.

PricedBomBuilder

Applies prices to BOM lines and computes totals — the shared math behind the priced BOM command and the live BOM palette.

PricedBomResult

A fully priced BOM: rows plus totals.

PricedRow

One priced BOM row. Unit prices are null when no source priced the part.

QuoteSections

The reserved section names and the rules for what belongs in a section.

Scene3DPlacement

The 2.5D→3D placement rule shared by the 3D view palette and any future 3D DWG export. World frame is AutoCAD's: X/Y the plan, Z up, inches. The library's 3D models anchor their ORIGIN on the component's mount plane (a deck's walking surface, an attachment's deck-edge mount, a post's base) — measured convention across the vault, validated by the collar math — so placement is a plain translate, never bounding-box re-anchoring.

SnapPoint

One mate point offered for capture, in world coordinates (the caller applies the host's block transform before choosing).

SnapResult

The capture decision: the outcome and, when snapped, the point.

StackCandidate

One placed deck as the stacking rule sees it: where its footprint stands, how far that footprint reaches from the insertion point, and which storey it belongs to.

StackResult

The stacking decision: the outcome, the deck it is about, and where the new deck goes.

StructureCheck

What the drawing declares about its structures, checked against what the geometry shows. Pure comparison: it reports, it never reassigns.

StructureGrouper

Which decks form one physical play structure, computed from the same shared-post adjacency PBGEN and PBFILL already use.

SubItemExploder

Explodes a tallied BOM into its sub-components by walking the parent → child links in PartsSubItems. Pure: the caller supplies the row lookup, so the walk is unit-testable without a database and the Cad layer's only job is running one query per level.

SubItemExplosion

An explosion pass: the sub-component lines plus what the pass could not trust. The notes exist because this data is hand-maintained — a silently dropped cycle or an unreadable quantity would turn into a short purchase list, so callers report them rather than presenting a clean total.

SubItemLine

One exploded sub-component: a part the drawing needs because a top-level component contains it.

SubItemRow

One PartsSubItems row as the explosion sees it. Every numeric column in that table is nvarchar, so the values arrive as raw text and are parsed here rather than at the database boundary — a price of "" or a quantity of "AR" is data the BOM has to survive, not an exception.

VaultComponent

A component parsed from a component-library 2D SVG. All coordinates are local to the component's insertion point with Y up (SVG is Y-down), in inches.

VaultDescription

What a vault root turned out to contain, for reporting before trusting it.

VaultInventory

Inspects a component-library root without assuming which of the two known layouts it is: the development tree keeps the family folders under {root}\library with the data files at the root, while a designer pointing PBVAULT at their own library usually names the family-folder level directly (…\Access Components\S0-1291\…) with the data files at that level or one above. Everything here is inspection only — no caching, no AutoCAD — so the plugin can describe a path BEFORE committing to it.

VaultMatePoint

A component mate point: where another component attaches and which way it faces.

VaultPolyline

One connected polyline run: vertices with AutoCAD-style bulges (bulge[i] curves the segment from vertex i to i+1; tan(sweep/4)).

VaultSvgParser

Minimal parser for the component library's machine-generated SVGs. They use a constrained vocabulary: a JSON metadata block (insertion point, post slots, mate points) and path elements using only absolute M/L/A/Z commands. Anything outside that vocabulary throws — callers fall back to placeholder geometry rather than render a wrong shape.

VaultXamlParser

Parser for the component library's native 2D geometry files — the legacy designer's own Component2D XAML ("{folder}.xaml"), the format the recovered library actually ships. It carries the same attachment metadata a design file's placed component does: the insertion point, the post slots, and the mate points (with their length class and mate-type). Produces the same VaultComponent contract as VaultSvgParser, so every downstream consumer (block build, filler pairing, mate snap) is source-agnostic.

Xaml3DAssets

Filename preference for the library's exported 3D models ("{folder}-3D.xaml"). Pure string work so the tolerance rules are testable: the vault is hand-maintained and its known misnamings — a "-3D2" suffix, a "-3D_NEW" variant, two parts' files sharing one misfiled folder — must resolve to the right model instead of silently dropping the part.

Xaml3DMeshes

Minimal reader for the component library's exported 3D XAML models. It extracts collar mesh bounding boxes — the input to CollarCounter — by scanning MeshGeometry3D resources whose key starts with Collar_ (case-insensitive across the library's old COLLAR_ and current Collar_ conventions; CollarHW_ is hardware, not a collar, and never matches because of the underscore). Pure text parsing — no WPF — so it runs and tests headlessly.
