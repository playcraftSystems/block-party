Developer Guide#

Architecture: the Core/Cad split#

The AutoCAD managed API cannot run headless and needs a licensed AutoCAD, so the solution is built around one hard rule:

┌────────────────────────────┐      ┌──────────────────────────────────┐
│  Playcraft.Core            │      │  Playcraft.Plugin                │
│  net10.0 - NO AutoCAD refs │◄─────│  net10.0-windows - AutoCAD.NET   │
│                            │      │                                  │
│  BOM tallying, features,   │      │  [CommandMethod] shims,          │
│  catalog parsing, geometry │      │  Transactions, SelectionFilter,  │
│  math, pricing formatting  │      │  XData tagging, palette UI       │
└────────────────────────────┘      └──────────────────────────────────┘
        ▲ fully unit-testable                 ▲ testable only with AutoCAD
          on any CI runner                      (self-hosted smoke tests)
  • Playcraft.Core owns every rule that can be expressed without AutoCAD: BOM math (BomCalculator), the feature catalog (FeatureCatalog), catalog payload parsing, post-merge geometry, SVG parsing. It has zero AutoCAD references and must build on Linux.
  • Playcraft.Plugin is a thin adapter: it collects data from the drawing (block references, XData tags), maps it into Core’s neutral types (PlacedComponent), calls Core, and writes results back to the drawing or command line.

The litmus test: if a change you’re making to Playcraft.Plugin contains an if worth unit-testing, the logic belongs in Core. Define the data shape (or an interface) in Core and implement the AutoCAD side as an adapter. See how Commands.TallyBom feeds BomCalculator.Tally for the pattern.

Extension points#

You want to… Do this
Add a command New [CommandMethod] in Playcraft.Plugin, delegate logic to Core, add the command to data/features.json
Add BOM behavior Extend BomCalculator (+ tests) in Core; adapters only collect inputs
Consume a new catalog field Extend CatalogPart in Core; the content hash automatically invalidates cached copies
Add UI WPF/PaletteSet code lives in Playcraft.Plugin; ViewModels with testable logic go to Core

The full walkthrough is on Adding a feature.

Testing model#

Suite Needs Where it runs
Playcraft.Core.Tests nothing everywhere (cloud CI gate, 80% line coverage on Core)
Playcraft.Plugin.SmokeTests (Category=RequiresAcad) AutoCAD 2027 installed self-hosted runner / dev workstation
build/smoke-accoreconsole.ps1 AutoCAD 2027 installed self-hosted runner; exercises real commands headless
build/golden-path.ps1 AutoCAD 2027 installed self-hosted runner; the full designer job end to end, with a coverage gate over every [CommandMethod]
build/drawing-regression.ps1 AutoCAD 2027 installed self-hosted runner; the generation chain over seven real production designs, diffed against recorded baselines

The golden path is the one that fails when you add a feature and forget to cover it. Its assertions are hand-written rather than a recorded transcript, on the grounds that a snapshot blesses whatever the code did last — every expected number carries a Why saying which rule produces it.

The drawing regression is the deliberate exception, and the two do not conflict because they answer different questions. The golden path pins numbers a human reasoned about; the drawing regression asks “did anything move that nobody mentioned?” over designs of 40–90 components that nobody will ever assert by hand. It exists because of a defect neither the oracles nor the golden path can see: changing deck enumeration order moves a shared post by less than the 1.0" merge tolerance, so no count changes and nothing goes red. Reversing enumeration leaves all 519 Core tests green and turns four of its scenarios red.

What stops it becoming the thing the golden path warns about is that a baseline can only be rewritten by -Accept, which refuses without a -Reason. The reason, the commit and the component-library fingerprint are written into the baseline, so accepting a change shows up in git diff as a sentence someone had to write rather than a silent block of moved numbers. That is a social gate enforced by code review, not proof that anyone understood the diff — so read the reason, and disbelieve “updated baselines”.

API reference#

The Playcraft.Core API reference is generated by DocFX from XML doc comments. The compiler enforces them (CS1591 is an error), so the reference is always complete.

Doc comments are public, so write accordingly#

This site (including the API reference) is published to the open internet. That gives comments a two-tier rule:

  • /// XML doc comments hold behavior, contracts, and usage. They are written for an outside reader and published verbatim by DocFX.
  • // regular comments hold internal endpoint paths, payload quirks, internal system names, and infrastructure notes. They never leave the repo.

If you’re documenting how our systems work rather than what this API does, it goes in a regular comment (see CatalogPayload in Catalog.cs for the pattern). The docs build enforces this: docs/build-docs.ps1 scans every generated page against the deny-list in docs/leak-patterns.txt and fails on a match. When you introduce a new internal endpoint, config key, or system name, add a pattern for it in the same PR.
